## Acceptance gate 3 — crash after publish/before mark causes duplicate delivery and eventual published mark

Automated: `crash_after_publish_before_mark_causes_duplicate_then_eventual_published_mark`.
Inserts one outbox row directly, configures the
`orders.outbox.after_broker_publish_before_mark_published` fault to fire
once, runs the publisher (the row is genuinely "published" to a counting
producer, then the simulated crash leaves it claimed and unpublished),
waits past its 200ms lease, and runs the publisher again with no fault
configured. Result: the row is claimed twice (`was_previously_claimed`
true the second time → `lease_recoveries_total == 1`), published twice
(`producer.calls == 2`), and ends with `published_at` set.

```
test crash_after_publish_before_mark_causes_duplicate_then_eventual_published_mark ... ok
```

Manually, live against Postgres + real Redpanda (see "Live end-to-end
check" below): the same scenario proven through the actual `RskafkaProducer`
and `/metrics`.

## Acceptance gate 4 — two publishers safely share backlog using skip-locked claims

Automated: `two_publishers_share_backlog_without_double_publish`. Inserts
40 rows directly, runs two `run_publisher_once` calls concurrently
(`tokio::spawn`, separate `claimed_by` identifiers, same pool), and
asserts: the two claim counts sum to exactly 40 (no overlap, no gap),
the shared `CountingProducer` was invoked exactly 40 times total (never
more — proving no row was published twice), and the backlog is fully
drained afterward.

```
test two_publishers_share_backlog_without_double_publish ... ok
```

Ran 5 consecutive times (`--test-threads=4`, full suite) to check for
raciness; all 5 runs passed with no flakes.

## Acceptance gate 5 — broker outage grows backlog; recovery drains it

Automated: `broker_outage_grows_backlog_then_drains_on_recovery`, using a
`FlakyProducer` test double (an `AtomicBool` toggled by the test) instead
of stopping the real Redpanda container — documented rationale in ADR
0005. Inserts 5 rows, runs the publisher while "down" (backlog stays at
5, failures recorded), waits past the backoff cap, flips the producer
"up," and polls the publisher until the backlog reaches 0.

```
test broker_outage_grows_backlog_then_drains_on_recovery ... ok
```
