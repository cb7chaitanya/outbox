## Live four-service verification

Postgres and Redpanda ran through Compose. Real `cargo run` processes were
started for orders, inventory, payments, and fulfilment. All four
`/health/ready` endpoints returned `200 ok`.

Happy-path order `01a01a07-8f3c-7361-b21e-6fbfaba118c7` converged:

`PENDING -> INVENTORY_RESERVED -> PAYMENT_AUTHORIZED -> READY_FOR_FULFILMENT -> COMPLETED`

The fulfilment database contained exactly one `CREATED` row for that order.

For failure-path order `01a01a0b-5301-7e72-b10f-fc92f10a3897`, the dev-only
`fulfilment.permanent_failure` fault was armed once. The order converged:

`PENDING -> INVENTORY_RESERVED -> PAYMENT_AUTHORIZED -> READY_FOR_FULFILMENT -> CANCELLING -> CANCELLED`

The reservation was `RELEASED`, the payment was `REFUNDED`, and cancellation
occurred only after both outcome events were consumed. Stock showed 98
available and 2 reserved afterward: only the separate successful order's two
units remained reserved, proving the failed order's three units were restored.

## Additional finding

The first long-lived-process run replayed historical broker records whose
orders existed only in ephemeral test databases. Three new outcome branches
initially returned infrastructure errors and retried forever. They were fixed
to use the established `UNKNOWN_ORDER` poison/DLQ path. The full integration
suite and live run were repeated after the fix.
