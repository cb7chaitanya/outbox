## Acceptance gate 2 — concurrent orders cannot oversell; stock invariant holds

Automated: `concurrent_reservations_never_oversell`. Seeds `SKU-CONTENDED`
with 5 available units, fires 10 concurrent `repository::reserve` calls
(each its own transaction, each requesting 1 unit) via `tokio::spawn`,
and asserts the outcome.

```
test concurrent_reservations_never_oversell ... ok
```

Result: exactly 5 `Active` and 5 `Rejected` outcomes (never more than 5
succeed), final `available_qty == 0`, `reserved_qty == 5`,
`available_qty >= 0` throughout, and `available_qty + reserved_qty == 5`
(invariant I5) — the `SELECT ... FOR UPDATE` row lock inside
`repository::reserve`'s transaction serializes the ten concurrent
transactions on the contended row rather than letting them race past each
other.

## Acceptance gate 3 — multi-SKU reservation is all-or-nothing

Automated: `multi_sku_reservation_is_all_or_nothing`. Seeds `SKU-PLENTY`
with 100 units and `SKU-SCARCE` with 1, requests 5 of the first and 10 of
the second in one reservation.

```
test multi_sku_reservation_is_all_or_nothing ... ok
```

Result: the reservation is `Rejected` with `reason_code:
"INSUFFICIENT_STOCK"`, and — critically — `SKU-PLENTY`'s `available_qty`
stays at 100 and `reserved_qty` stays at 0: the SKU that *did* have
enough stock is never touched when any other line in the same
reservation fails.

## Acceptance gate 4 — crash after DB commit/before offset commit produces no duplicate effect

Automated: `crash_after_db_commit_before_offset_commit_has_no_duplicate_effect`.
Publishes one `reserve_inventory` command, arms the
`inventory.after_db_commit_before_offset_commit` fault for exactly one
firing, drains once (the business transaction commits — reservation
created, stock decremented — then the fault fires and the offset ledger
is *not* advanced past that record), then drains again with the fault
gone (simulating a restart: the same record is refetched from the
unchanged offset).

```
test crash_after_db_commit_before_offset_commit_has_no_duplicate_effect ... ok
```

First drain: `stopped_by_fault == true`, `applied == 1`, one reservation
row exists, `reserved_qty == 3`. Second drain (redelivery): `duplicate ==
1`, `applied == 0`, still exactly one reservation row, `reserved_qty`
still `3` — the inbox row committed inside the first pass's business
transaction makes the redelivered record a genuine no-op, exactly as
spec section 14 describes ("redelivery becomes a no-op because of the
inbox row").

## Live end-to-end check

Started `orders` and `inventory` as real processes against the Compose
infrastructure (not test doubles), seeded stock via the dev endpoint, and
created a real order through the public HTTP API:

```
$ curl -X PUT localhost:8082/_dev/stock/SKU-LIVE-1 -d '{"available_qty": 50}'
{"sku":"SKU-LIVE-1","available_qty":50,"reserved_qty":0,"fulfilled_qty":0,"version":1,...}

$ curl -X POST localhost:8081/v1/orders \
    -H "Idempotency-Key: live-smoke-test-key-001" \
    -d '{"items":[{"sku":"SKU-LIVE-1","quantity":5,"unit_price_minor":100}],"currency":"USD"}'
{"id":"01a0199e-7830-7573-a1d6-bab122a83d34","status":"PENDING",...,
 "correlation_id":"01a0199e-7830-7573-a1d6-ba708c7c9653",...}

# ~3 seconds later, no manual intervention:
$ curl localhost:8082/_dev/stock/SKU-LIVE-1
{"sku":"SKU-LIVE-1","available_qty":45,"reserved_qty":5,"fulfilled_qty":0,"version":2,...}
```

`available_qty` moved 50→45 and `reserved_qty` 0→5 purely from the order
API call — orders committed the order, its outbox published both
`orders.order_created` and `inventory.reserve_inventory` in the same
transaction, and inventory's consumer picked the command up, reserved the
stock, and replied. Confirmed via `rpk topic consume inventory.events.v1`
that the resulting `reservation_succeeded` envelope carried
`causation_id` equal to the `reserve_inventory` command's `event_id` and
`correlation_id` equal to the order's correlation ID — the full
correlation/causation chain (spec section 16) holds end-to-end, not just
within one service.

Both manually-started processes were killed after the check; Compose
infrastructure (Postgres/Redpanda) was left running for M05.
