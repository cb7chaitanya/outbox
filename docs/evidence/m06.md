# M06 acceptance evidence — Choreographed workflow and compensation

All commands below were actually run in this repository state on
2026-08-19, against the M00-M05 infrastructure (still running: Postgres,
Redpanda, Redpanda Console).

## Scope delivered

- Fixed the M05-flagged version-counter debt: a real per-`(order_id,
  target)` outbound command sequence (`outbound_command_sequences` table,
  `repository::reserve_command_version`) replaces the hardcoded
  `aggregate_version: 1`/`order_version` reuse both `authorize_payment` and
  `reserve_inventory` relied on. See `docs/adr/0011-per-target-command-version-counter.md`.
- `orders.reservation_id` column, populated on `reservation_succeeded`, so
  a later `payment_failed` can build `release_inventory`'s payload without
  a cross-service join.
- Inventory: `repository::release` (idempotent — a redelivered or
  duplicate release against an already-`RELEASED` reservation is a
  no-op) and `inventory.commands.v1` dispatch extended to handle
  `release_inventory` alongside `reserve_inventory`, emitting
  `inventory_released`.
- Orders' outcome consumer now dispatches across both
  `inventory.events.v1` and `payments.events.v1` by `event_type`:
  `reservation_succeeded` (unchanged behavior, real command version),
  `reservation_failed` (now real compensation:
  `PENDING`→`CANCELLING`→`CANCELLED`, matrix row 1), `payment_authorized`
  (`INVENTORY_RESERVED`→`PAYMENT_AUTHORIZED`), `payment_failed` (emits
  `release_inventory`, →`CANCELLING`, matrix row 2), `inventory_released`
  (→`CANCELLED`, matrix row 2's confirmation half).
- A real bug found and fixed by this milestone's own live end-to-end
  check: `TransitionError::NotFound` was propagated as a fatal `Err`,
  wedging the consumer's offset ledger forever on any record naming an
  order the consumer's database has no row for (cross-talk on the shared
  dev Kafka broker from earlier automated test runs surfaced this
  immediately). Fixed to DLQ as `UNKNOWN_ORDER` instead (invariant I15).

No service made a synchronous HTTP call to another — every transition was
driven by consuming a real Kafka record; confirmed by code inspection
(orders' `http.rs` handler never calls out to inventory/payments, and the
outcome consumer only reacts to consumed events) and by the timing above
(three independent background poll loops, ~1s apart).

**Real bug caught by this exact run** (first attempt): the order stayed
`PENDING` forever, with orders logging `"outcome consumer batch failed",
"error":"order not found"` in an infinite loop on both topics. Root cause
and fix: see "Scope delivered" above and
`docs/adr/0011-per-target-command-version-counter.md`'s sibling commit
`fix(orders): DLQ unknown-order outcomes instead of wedging the consumer`.
After the fix, the same live run (fresh processes) drained ~200 backlogged
poison records from earlier automated test runs sharing the dev broker
(`"processed outcome batch","poison":115` etc.) and then applied the real
order's records within the same batch — reaching `PAYMENT_AUTHORIZED` in
under 2 seconds total.

`choreography_tests.rs::payment_failure_releases_inventory_then_cancels`:

```
$ cargo test -p orders --test choreography_tests payment_failure_releases_inventory_then_cancels
```

Asserts, in order: after `payment_failed`, order is `CANCELLING` (**not**

### Gate 4 — duplicated and reordered outcomes do not create illegal transitions

`choreography_tests.rs::duplicated_and_reordered_outcomes_do_not_create_illegal_transitions`:

```
$ cargo test -p orders --test choreography_tests duplicated_and_reordered_outcomes_do_not_create_illegal_transitions
test duplicated_and_reordered_outcomes_do_not_create_illegal_transitions ... ok
```

Asserts: `payment_authorized` delivered while the order is still `PENDING`
(reservation_succeeded not yet processed) is inbox-marked but produces no
transition (order stays `PENDING`, not crashed, not forced into an illegal
state) — the `TransitionError::IllegalTransition` branch, logged and
skipped. A raw redelivery (identical bytes, same `event_id`) of
`reservation_succeeded` is recognized as a duplicate (`applied: 1,
duplicate: 1`) and still reaches `INVENTORY_RESERVED` correctly.

A second, related regression test
(`unknown_order_reference_does_not_block_the_partition`) proves the
poison-isolation fix from the "Scope delivered" section: a record naming
an unknown order is DLQ'd, and a valid record right behind it on the same
topic still applies.

## Scope boundary carried into M07

Compensation matrix rows 3 and 4 (fulfilment failure → refund payment +
release inventory; compensation retry exhaustion → `MANUAL_REVIEW`) are
**not** implemented — they depend on the fulfilment service, which does
not exist until M07. `orders::domain::OrderStatus::Cancelling` and the
release/refund command-emission pattern established here are built
generally enough that M07 adds the third row (refund + release together)
without restructuring: it needs a `payments.refund_payment` emission
alongside the existing `release_inventory` one, tracking that both
compensations are confirmed before the final `CANCELLED` transition
(currently only one compensation — release — is ever pending at a time, so
there is no "wait for both" logic yet; M07 must add it).
