# M05 evidence — payments with retry taxonomy

**Date:** 2026-08-19
**Environment:** local Docker Compose (Postgres 16.4 on host port 55432,
Redpanda v24.2.7 on `localhost:19092`), Rust 1.94.0, macOS/aarch64.

All commands below were run against the real Postgres/Redpanda containers
started by `make up`, using `.env` for connection settings. Nothing here
is asserted without having actually been run in this repository state.

## Acceptance gate 1 — timeout then success authorizes once

Automated: `timeout_then_success_authorizes_once` in
`services/payments/tests/consumer_tests.rs`. Configures
`FAULT_PROVIDER_TIMEOUT` to fire once for this order's idempotency key,
publishes one `authorize_payment` command, drains the consumer.

```
$ DATABASE_URL=postgres://outbox_dev:***@localhost:55432/payments \
  REDPANDA_BROKER=localhost:19092 \
  cargo test -p payments --test consumer_tests timeout_then_success_authorizes_once

running 1 test
test timeout_then_success_authorizes_once ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out
```

Asserted: `summary.applied == 1`, `summary.poison == 0`,
`provider.real_authorize_calls() == 1` (the timeout attempt recorded
nothing; only the retry did real work), exactly one `AUTHORIZED` row in
`payments`, exactly one `payments.payment_authorized` outbox row.

simulating a dropped response. The handler's in-transaction retry then
hits the provider's own idempotency-key ledger.

```

test lost_success_response_then_retry_creates_one_provider_operation ... ok
```

Asserted: `summary.applied == 1`, `provider.real_authorize_calls() == 1`

against the running Compose infrastructure (`DELIVERY_MODE=outbox`),

Full chain — `POST /v1/orders` → `orders.order_created` +
`inventory.reserve_inventory` (same outbox transaction) →
inventory reserves stock, emits `reservation_succeeded` → orders'

(same transaction) → payments authorizes against the fake provider,
emits `payment_authorized` — completed in well under a second, with no
manual intervention.

### A real bug this caught

The *first* attempt at this live check DLQ'd `authorize_payment` with
`EXPECTED_VERSION_GAP` — the command's envelope carried the order's own
version (2) rather than a version meaningful to payments' own
`consumer_aggregate_versions` tracking (which expected 1, having never
seen a message for this order before). Fixed in
`services/orders/src/outcome_consumer.rs` (commit `f29bd4b`) by using a
fixed `aggregate_version: 1` for this command — correct because it's the
only command orders sends to payments in this milestone's scope. Full
rationale, including the M06 prerequisite this creates (a real
per-downstream-consumer counter, needed once `refund_payment` becomes a
second command on the same relationship), is in
`docs/adr/0010-orders-consumes-reservation-outcomes.md`. This bug was
invisible to the unit and per-service integration suites, which never
exercised the full three-service chain — the live check is what
surfaced it, and the fix was verified by repeating the exact same live
check afterward and confirming a clean `AUTHORIZED` row.
