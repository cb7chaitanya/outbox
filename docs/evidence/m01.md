# M01 acceptance evidence — Orders API and local consistency

All commands below were actually run against this repository state on
2026-08-19, with the M00 Compose infrastructure (Postgres on host port
`55432`, Redpanda) already up.

## Acceptance gate 1: concurrent identical idempotent requests yield one order and same response

Repository-layer test (`services/orders/tests/repository_tests.rs`):
10 concurrent `create_order` calls with the same idempotency key and body
against a freshly migrated database.

```
$ DATABASE_URL=postgres://outbox_dev:outbox_dev_password@localhost:55432/orders \
    cargo test -p orders --test repository_tests concurrent_identical_idempotent_requests_yield_one_order
running 1 test
test concurrent_identical_idempotent_requests_yield_one_order ... ok
test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out
```

Asserts: all 10 callers observe the same order id; `select count(*) from
orders` is 1; `select count(*) from order_items` is 2 (not 20).

HTTP-layer test (`services/orders/tests/http_tests.rs`): 8 concurrent
`POST /v1/orders` calls through the real Axum router.

```
$ cargo test -p orders --test http_tests concurrent_identical_http_requests_yield_one_order_and_same_response
running 1 test
test concurrent_identical_http_requests_yield_one_order_and_same_response ... ok
test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out
```

Asserts: all 8 callers get `202 Accepted`; the set of observed order ids
has size 1; the set of observed full response bodies (serialized) has
size 1 — i.e. every caller saw the identical response, not just the same
order id.

Manual confirmation (see also section "Manual smoke test" below):
concurrent identical `curl` requests against a running instance return the
same order id and body.

## Acceptance gate 4: illegal and stale transitions fail without partial writes

```
$ cargo test -p orders --test repository_tests illegal_transition_is_rejected_without_partial_write
test illegal_transition_is_rejected_without_partial_write ... ok

$ cargo test -p orders --test repository_tests stale_expected_version_is_rejected_without_partial_write
test stale_expected_version_is_rejected_without_partial_write ... ok
```

Each test creates a `PENDING` order, then:

- **Illegal:** attempts `PENDING -> COMPLETED` (skips the required graph)
  with the correct current version. Asserts `TransitionError::
  IllegalTransition { from: Pending, to: Completed }`, then reloads the
  order and asserts `status` and `version` are unchanged and
  `order_transitions` still has exactly 1 row (the creation row).
- **Stale:** attempts the legal transition `PENDING ->
  INVENTORY_RESERVED` but with `expected_version = order.version + 41`.
  Asserts `TransitionError::VersionConflict { expected: 42 }`, then
  reloads the order and asserts the same "nothing changed" invariants.

A companion positive test
(`legal_transition_with_correct_version_succeeds_and_is_recorded`) proves
the same code path *does* apply a legal, correctly-versioned transition
(version becomes 2, a second `order_transitions` row is recorded with
`from_status = PENDING`), so the negative tests are demonstrating
rejection, not a code path that can never succeed.

state; test databases created by `#[sqlx::test]` are ephemeral and
already isolated from this.

## Scope note: what M01 deliberately does not include

Per the M01 milestone description ("No broker publish yet except a
stub/port"), `orders` does not publish to Kafka/Redpanda in this
milestone — that starts in M02 (naive dual-write) and is corrected in M03
(transactional outbox). `POST /v1/orders/{id}/cancel` is optional per
spec section 10 and is deferred until the choreographed workflow (M06+)
gives cancellation something real to do. `transition_order` in
`repository.rs` is exercised only by tests in M01 — no HTTP endpoint
calls it yet, since the only order-creating actor right now is the
client itself and the only reachable status is `PENDING`.
