## Acceptance gate 2: both required dual-write failure tests reproduce and explain inconsistency

Deterministic, automated (`services/orders/tests/dual_write_tests.rs`),
run against real Postgres (`#[sqlx::test]`, fresh migrated DB) and real
Redpanda:

```
$ DATABASE_URL=postgres://outbox_dev:outbox_dev_password@localhost:55432/orders \
    REDPANDA_BROKER=localhost:19092 \
    cargo test -p orders --test dual_write_tests -- --test-threads=1
running 2 tests
test dual_write_db_commit_without_event ... ok
test dual_write_publish_then_retry_duplicate ... ok
test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 2.14s
```

- `dual_write_db_commit_without_event`: configures
  `orders.after_db_commit_before_publish` (fail_next=1), issues one
  `POST /v1/orders`, asserts `503 INJECTED_FAULT`, queries the order back
  by `idempotency_key` directly against Postgres (row exists), then reads
  the entire `orders.events.v1` topic from the earliest offset and
  asserts zero envelopes have that order's `aggregate_id`.
- `dual_write_publish_then_retry_duplicate`: configures
  `orders.after_publish_before_response` (fail_next=1), issues a first
  `POST` (asserts `503`), then a retry with the same `Idempotency-Key`
  (asserts `202`, single order id), then asserts **exactly two** matching
  envelopes on the topic for that `order_id`, with two distinct
  `event_id`s.

Live, human-readable reproduction via `make demo-naive-failure`
(`scripts/demo-dual-write-failure.sh`, builds and runs `orders` itself
with `DELIVERY_MODE=naive FAILURE_INJECTION_ENABLED=true`, tears it down
on exit), full run, exit code 0:

## Acceptance gate 3: evidence includes correlation IDs, DB state, and observed Kafka records

- **Correlation IDs**: every envelope published in naive mode carries the
  order's `correlation_id` (generated or client-supplied per M01) and a
  fresh `causation_id` per publish attempt — see
  `services/orders/src/http.rs::publish_naive`. The `dual_write_tests.rs`
  assertions decode the full `Envelope<OrderCreatedPayload>` (not just
  checking status codes), so `correlation_id`/`causation_id`/
  `aggregate_version` are all exercised by the passing tests above, and
  the demo script's `request_id` (a `problem+json` field, spec section
  10) is visible in the transcript above (`"request_id":
  "01a0173c-022a-7851-8c77-09cd2d2a3420"`).
- **DB state**: `dual_write_db_commit_without_event` queries `orders`
  directly by `idempotency_key`; the demo script does the same via
  `docker compose exec postgres psql`.
- **Observed Kafka records**: both the Rust tests (via `rskafka`
  `fetch_records` from `OffsetAt::Earliest`) and the shell demo (via
  `rpk topic consume -o start`) read real records back from the broker
  and filter/count by `aggregate_id`, not by trusting the HTTP response
  alone.

## Acceptance gate 4: `docs/failure-lab.md` explicitly concludes retries do not make two systems atomic

See `docs/failure-lab.md`, "Conclusion" section: *"Retries alone cannot
make two independently-committing systems — Postgres and Kafka — atomic
with each other... Both failure modes are consequences of the same root
cause: the business state change and the event publication are not one
atomic unit."*

## Not in scope for M02 (explicitly deferred)

- No `outbox_events` table exists (spec section 1's non-negotiable
  progression rule; lands in M03).
- `DELIVERY_MODE=outbox` is accepted by config parsing (so `.env` can
  name it without erroring) but has no implementation — only `naive` is
  real until M03.
- Kafka message headers (`event_id`, correlation/causation headers,
  producer name) are not set on the naive publish — spec section 13
  requires them for the *outbox* publisher specifically; the envelope's
  JSON body already carries all of that metadata, and M02's producer is
  intentionally minimal. Revisit when M03 builds the real publisher.
